3. 构建动态库

静态库的缺点如下：

  1. 难以维护，如果修改，必须重新编译和链接所有使用该静态库的程序
  2. 浪费空间，因为静态库的目标问及那在编译过程中被链接到最终的程序中，所以每一个链接了静态库的程序都相当于将静态库的目标代码复制了一份

动态库就是为了解决静态库的维护问题和空间利用问题而产生的，动态库也称为动态链接库(dll)或共享库，与静态库不同，动态库的目标代码是在程序装载时或运行时被动态链接的，而非在编译过程中静态链接的，这样动态库与使用动态库的程序就在编译器做到了解耦。

Windows 和 Linux 操作系统的动态链接机制有些差异，这也导致其构建过程会有一点不同。

Windows 中动态链接的原理

当启动进程时，Windows 操作系统会装载进程所需的动态链接库，并调用动态链接库的入口函数。由于 64位 Windows 操作系统默认启用地址空间布局随机化(ASLR)特性，动态链接库被装载时，会根据特定规则随机选取一个虚拟内存地址进行装载，这就意味着其编译后的机器代码中，凡是访问内存某一绝对位置的代码，在装载时都需要被改写，这就是重定位。在 32位 Windows 操作系统中，ASLR 没有默认开启。此时，动态链接库将会被装载到偏好基地址处，偏好基地址是编译时指定的，不过在装载时，这个地址未必总是可用的，当多个动态链接库都设置了同一个偏好基地址(如均采用默认值)，然后被同时装载到一个进程时，就会出现冲突，就需要重定位了。

ASLR 特性是一个计算机安全特性，主要用户防范内存被恶意破坏并利用。它的存在使得动态链接库装载的内存地址是不固定的。

事实上，Windows 操作系统并没有总是对动态链接库进行重定位，一旦确定了某一动态链接库装载的虚拟内存地址，然后任何进程再用到同一个动态链接库时，都会将它装载到同一个虚拟内存地址中。

当动态链接库不被所有进程使用后，它会被操作系统从内存中卸载；当它又被重新使用并装载时，其装载位置有可能发生变化，单操作系统并不保证这一点，所以重启操作系统是唯一能够保证动态链接库装载地址发生随机改变的方法。

Linux 中动态链接的原理

Linux 操作系统同样具有 ASLR 特性，通常情况下，每一个进程被创建时，都会将其可执行文件及其链接的动态库装载到不同的随机虚拟地址。Linux 并没有采用 Windows 的装载重定位方式，即在装载时根据实际的内存布局修改代码中的地址。而是采用了一种跳板(trampoline)的机制，其通常是一小段代码，用于在运行时动态地计算目标地址，然后跳转到该地址。

这是因为 Linux 操作系统较为激进，每次启动进程时，动态库的装载地址都是完全随机的，并没有像 Windows 一样有一个特定规则，如果直接对代码中的访存地址进行重定位，这段代码就无法共享。Linux 通过使用 地址无关代码 (PIC) 来解决共享这一问题，当启用地址无关代码后，目标代码访问全局变量，调用全局函数时，都会使用全局偏移表 (GOT) 做一次中转。也就是说，目标代码中访问的内存地址实际上对应 GOT 某个位置，这个位置记录了要访问的变量或调用的函数的实际内存地址，由于动态链接库会在运行时被装载到随机的内存地址中，则 GOT 各个表项的值只能在运行时被替换。

实际上，Linux 也支持类似 Windows 操作系统中通过静态重定位实现动态链接的方式，不过此时动态库不能在物理内存中共享了。

使用 GCC 和 make 构建

当运行主程序时，Linux 系统的动态链接器必须能够找到主程序所需的动态库，但它默认只会在系统配置的一些目录下搜索动态库，而不会考虑当前目录。包含搜索路径的配置文件位于 /etc/ld.so.conf。为了运行程序就去修改系统配置显然是不合理的。动态连接器还可以根据环境变量 LD_LIBRARY_PATH 的值来搜索动态库。

Linux 可执行文件的动态节中有两个与动态库搜索路径相关的条目，一个是 RPATH，一个是 RUNPATH。二者的区别在于优先级，动态链接库会按照下面列举的顺序依次搜索：

  1. 动态节中的 RPATH 项指定的路径。
  2. 环境变量 LD_LIBRARY_PATH 指定的路径。
  3. 系统配置文件 /etc/ld.so.conf 指定的路径。
  4. 动态节中的 RUNPATH 项指定的路径。

RPATH 在一些问题上很有用，例如程序依赖某一特定版本的系统库，并将这一系统库与程序一同打包发布，希望程序使用打包提供的这一个版本的系统库，而不是去系统搜索路径中搜索系统自带的版本。如果是类似现在所遇到的找不到库的情况，指定 RUNPATH 就是推荐的方法，因为这样可以把链接库存放位置的决定权留给用户。

1. 引用 Boost C++ 头文件

头文件库指只包含头文件(.h, .hpp等) 的程序库。使用这种库非常方便，只需要在程序中引用它的头文件，无须对库本身进行额外的编译。源程序引用头文件，相当于复制了头文件的内容，这样头文件库实际上也就称为了引用它的程序的一部分，所以使用头文件库只需编译引用它的程序，头文件库代码会一同编译。

除了用起来简单，头文件库在性能方面也更具有优势，这是因为它能够直接被程序以源代码的形式引用，编译器能够更好地进行代码优化，如实现更多的函数内联，有助于提升程序的整体性能。

其缺点也很明显，那就是影响编译时间，因为头文件库本身没有源程序，无法独立编译成目标文件，再被链接到使用它的程序中，这就不可避免地需要反复编译头文件中的程序，另外分发头文件库也意味着开源是必须的，比较需要用户来编译，这反映了头文件库的封装性相对较差。

即使用头文件库有简单，运行高效两个较大的优势，缺点是影响编译时间以及代码必须公开。对于较为常用且简单的库，尤其是追求极致性能的库，使用头文件库的形式非常合适。

导入头文件有两种方式：使用 <> 导入和使用 “” 导入

5. 到处编译的共同需求

1. 构建的基本单元：源程序

如果不把头文件当作源程序，那么源程序就是会被编译器百衲衣成目标文件的文件。源程序可以看作构建过程中最基本的组成单元。构建时，应当根据源程序所采用的编程语言，使用对应的编译器。同时还根据一些特殊的构建要求，确定编译时传递的参数。

  1. 头文件搜索目录
  2. 链接库文件搜索目录
  3. 宏定义
  4. 其他编译链接参数等(如编译优化选项等)

2. 核心的抽象概念：构建目标（乱七八糟的概念）

将一些目标文件打包或链接成库文件或可执行文件，这样这些库文件和可执行文件就可以称作构建目标了，也称为 二进制构建目标，其包括以下类型：

  1. 可执行文件
  2. 一般库（包含静态库和动态库）
  3. 目标文件库

目标文件库就是目标文件的集合。

伪构建目标指的是不产生二进制文件的构建目标，包含以下三种类型：

  1. 接口库
  2. 导入目标
  3. 别名目标

3. 目标属性

  1. 头文件搜索目录
  2. 链接库文件搜索目录
  3. 宏定义
  4. 其他编译链接参数等

下面以构建动态库为例子，感受构建要求和使用要求之间的联系。

Windows 中动态库构建目标的要求

下面两条规则编译构建目标的源程序 a.c 到目标文件 a.obj，并通过 /link, /dll, /out:liba.dll 和 def:liba.def 等参数链接当前构建目标所对应的目标文件 a.obj，这就是 liba.dll 这个动态库构建目标的构建要求。

下面两条规则指定 liba.lib 导入库文件名作为链接参数，就是 liba.dll 动态库构建目标的使用要求。main.exe 作为一个该动态库的使用者，会将 liba.lib 与主程序编译后的目标文件 main.obj 一同链接。这里也体现了动态库构建目标的使用要求会被传递给主程序，作为主程序构建要求的一部分。

Linux 中动态库构建目标的要求

下面两条规则实际上声明了动态库 liba.so 这个构建目标的构建要求：使用 -fPIC 参数编译构建目标的源程序 a.c 到目标文件 a.o，使用 -shared 参数将目标文件链接称最终的动态库。

主程序的构建要求包括在链接过程中通过 -L. 参数指定链接库搜索目录，并通过 -la 参数指定链接库的名称。这同时也是动态库构建目标的使用要求，动态库的使用要求会传递到主程序的构建要求之中。

伪构建目标不需要被构建，自然也就不存在对应的构建要求，而只存在使用要求。

4. 使用要求的传递性

设有可执行文件 main，其使用了库 B，而库 B 又使用了库 A.

如果库 B 中的某个函数可能返回一个在库 A 中定义的类型，main 又调用了库 B 中的该函数，这就意味着 main 间接使用了库 A。具体来说，main 一定是引用了库 B 的某个头文件，而该头文件中直接或者间接地引用了库 A 的头文件。既然 main 间接地引用了库 A 的头文件，也就意味着 main 应该根据库 A 的使用要求来链接它，这种情形称作 “递归传递”。然而，如果库 B 不会在接口处暴露库 A 中定义的符号，而且 main 本身也不存在对库 A 的直接引用，那么库 A 的使用要求自然也不必传递给 main 了。

5. 目录属性

按照目录为源程序统一设置属性，能够带来极大的便利，例子如下：

  1. 对整个代码仓库设置 “将警告作为错误” 编译选项
  2. 需要构建的第三方库代码一般会放到 thirdparty 目录中，而这些代码可能在构建过程中产生大量的警告信息，我们需要对 thirdparty 目录中的代码禁用 “将警告作为错误” 这个编译选项
  3. 某些库的源程序分别位于不同目录，但头文件都在 include 目录中，我们希望能够为它们统一设定头文件搜索目录。

对第一个例子，可以对整个代码仓库的顶层目录设置编译选项的相关的属性；针对第二个例子，只需对 thirdparty 这个目录进行相关设置；针对第三个例子，同样只需对这些库的源程序所在目录在父目录设置头文件搜索目录的属性，就可使其子目录的每一个库都统一使用该属性。
